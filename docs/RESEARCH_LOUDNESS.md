# RESEARCH: Building a true loudness normalizer / loudness equalizer for real-time audio (browser)

Primary-source technical reference for a browser extension that normalizes the loudness of browser tabs.

**See also:** `docs/RESEARCH_COMFORT_NORMALIZER.md` — the design companion (comfort target and the delivery-versus-listening distinction, the published DRC/levelling profiles with numbers, the two-loop structure, the anti-maximiser bounds, frequency-domain loudness compensation, and the user-trim-versus-target distinction). **Scope rule for this document.** Every claim carries a URL. Standards and constants are quoted verbatim. Where a primary source is paywalled or access-restricted, that is stated and the closest free primary implementation is cited and explicitly labelled as a *secondary confirmation*. ## 1. ITU-R BS.1770 loudness algorithm, exactly

Primary sources:

- ITU-R **BS.1770-4** (10/2015), *Algorithms to measure audio programme loudness and true-peak audio level* — PDF (free, "Free Download"): <https://www.itu.int/dms_pubrec/itu-r/rec/bs/R-REC-BS.1770-4-201510-S!!PDF-E.pdf>
  (recommendation landing page: <https://www.itu.int/rec/R-REC-BS.1770-4-201510-S/en>)
- ITU-R **BS.1770-5** (11/2023), same title, currently in force, supersedes -4 — PDF: <https://www.itu.int/dms_pubrec/itu-r/rec/bs/R-REC-BS.1770-5-202311-I!!PDF-E.pdf>

BS.1770-4 and -5 are **identical for Annex 1 (loudness) and Annex 2 (true peak)**; -5 adds Annex 3 (advanced sound systems) and Annex 4 (object-based). The -4 PDF is still downloadable but only via the "Free Download" tree under the document page; the `-4-...-I!!PDF-E.pdf` shortcut that circulates on the web 404s. All quotes below are from the **-4** PDF, cross-checked against **-5**.

### 1.1 The algorithm (four stages), verbatim

> "The algorithm consists of four stages:
> – "K" frequency weighting;
> – mean square calculation for each channel;
> – channel-weighted summation (surround channels have larger weights, and the LFE channel is excluded);
> – gating of 400 ms blocks (overlapping by 75%), where two thresholds are used:
> – the first at −70 LKFS;
> – the second at −10 dB relative to the level measured after application of the first threshold."

> "The first step of the algorithm applies a 2-stage pre-filtering¹ of the signal. The first stage of the pre-filtering accounts for the acoustic effects of the head, where the head is modelled as a rigid sphere."

> Footnote 1: "The K-weighting filter is composed of two stages of filtering; a first stage shelving filter and a second stage high-pass filter."

> "The frequency weighting in this measure, which is generated by the pre-filter (concatenation of the stage 1 filter to compensate for the acoustics effects of the head, and the stage 2 filter, **the RLB weighting**) is designated K-weighting."

So: **stage 1 = high-shelf ("pre-filter", spherical-head model); stage 2 = RLB high-pass.** Filter order = stage 1 then stage 2.

### 1.2 Both stages: transfer functions and coefficients

Both stages are **second-order IIR (biquad) sections**, `H(z) = (b0 + b1 z⁻¹ + b2 z⁻²) / (1 + a1 z⁻¹ + a2 z⁻²)`.

**Stage 1 — high-shelf.** BS.1770-4, Table 1, *"Filter coefficients for stage 1 of the pre-filter to model a spherical head"* (verbatim, for 48 kHz):

| | |
|---|---|
| b0 | `1.53512485958697` |
| b1 | `−2.69169618940638` |
| b2 | `1.19839281085285` |
| a1 | `−1.69065929318241` |
| a2 | `0.73248077421585` |

**Stage 2 — RLB high-pass.** BS.1770-4, Table 2, *"Filter coefficients for the second stage weighting curve"* (verbatim, for 48 kHz):

| | |
|---|---|
| b0 | `1.0` |
| b1 | `−2.0` |
| b2 | `1.0` |
| a1 | `−1.99004745483398` |
| a2 | `0.99007225036621` |

> "These filter coefficients are for a sampling rate of 48 kHz. Implementations at other sampling rates will require different coefficient values, which should be chosen to provide the same frequency response that the specified filter provides at 48 kHz. The values of these coefficients may need to be quantized due to the internal precision of the available hardware. Tests have shown that the performance of the algorithm is not sensitive to small variations in these coefficients."

**The generic (sample-rate-independent) form is not printed in BS.1770.** The document gives only the 48 kHz coefficients plus the instruction above. The generic *design parameters* used by the reference implementation are (libebur128, `ebur128.c`, `ebur128_init_filter()`; <https://raw.githubusercontent.com/jiixyj/libebur128/master/ebur128/ebur128.c>):

```c
double f0 = 1681.974450955533;
double G  = 3.999843853973347;
double Q  = 0.7071752369554196;
double K  = tan(M_PI * f0 / (double) st->samplerate);
double Vh = pow(10.0, G / 20.0);
double Vb = pow(Vh, 0.4996667741545416);

double a0 = 1.0 + K / Q + K * K;
pb[0] = (Vh + Vb * K / Q + K * K) / a0;
pb[1] = 2.0 * (K * K - Vh) / a0;
pb[2] = (Vh - Vb * K / Q + K * K) / a0;
pa[1] = 2.0 * (K * K - 1.0) / a0;
pa[2] = (1.0 - K / Q + K * K) / a0;

/* stage 2 */
f0 = 38.13547087602444;
Q  = 0.5003270373238773;
K  = tan(M_PI * f0 / (double) st->samplerate);
ra[1] = 2.0 * (K * K - 1.0) / (1.0 + K / Q + K * K);
ra[2] = (1.0 - K / Q + K * K) / (1.0 + K / Q + K * K);
```

(Stage 2's numerator is the fixed `rb = {1.0, -2.0, 1.0}`. libebur128 then convolves the two biquads into one 5-tap IIR, which is an implementation choice, not part of the standard.)

**Validation of the generic form.** Evaluating the libebur128 design equations at `fs = 48000` reproduces BS.1770-4/-5 Table 1 and Table 2 to 15 significant digits:

```
fs = 48000
  stage1 shelf   b0=1.535124859586970 b1=-2.691696189406381 b2=1.198392810852850 a1=-1.690659293182410 a2=0.732480774215850
  stage2 RLB HP  b0=1.000000000000000 b1=-2.000000000000000 b2=1.000000000000000 a1=-1.990047454833980 a2=0.990072250366210
```

That is an exact match to the published tables, so the same equations evaluated at another rate are the intended generalisation.

**Coefficients at 44 100 Hz** (computed by evaluating the equations above verbatim at `fs = 44100`; same script that reproduces the 48 kHz tables above):

```
  stage1 shelf   b0=1.530841230050348 b1=-2.650979995154730 b2=1.169079079921587 a1=-1.663655113256020 a2=0.712595428073225
  stage2 RLB HP  b0=1.000000000000000 b1=-2.000000000000000 b2=1.000000000000000 a1=-1.989169673629796 a2=0.989199035787039
```

**K-weighting gain sanity check** (same script): the cascade gain at 997 Hz is `+0.6910 dB`, which is exactly what BS.1770 Note 1 requires (see §1.5). At 2000 Hz it is `+3.07 dB`; at 12 000 Hz `+4.04 dB` (approaching the stage-1 shelf gain G ≈ +4 dB).

### 1.3 Block structure, hop, and per-channel mean square

> "A gating block is a set of contiguous audio samples of duration Tg = 400 ms, to the nearest sample. The overlap of each gating block shall be 75% of the gating block duration. The measurement interval shall be constrained such that it ends at the end of a gating block. Incomplete gating blocks at the end of the measurement interval are not used."

Mean square of the *j*-th gating block of the *i*-th channel — BS.1770-4 Eq. (3):

```
z_ij = (1/Tg) ∫[j·Tg·step , (j+1)·Tg·step] y_i² dt ,   where step = 1 − overlap
       and  j ∈ { 0, 1, 2, … , (T/Tg) − step }
```

where `y_i` is the K-filtered input of channel `i`, `i ∈ I = {L, R, C, Ls, Rs}`.

Consequences that matter for an implementation:

- **Block = 400 ms; overlap = 75%; hop = 25% of the block = 100 ms** (`step = 1 − 0.75 = 0.25`).
- Blocks are **contiguous and aligned to the start of the measurement**, i.e. block *j* starts at `j · 0.25 · Tg`. A new 400 ms block is emitted every 100 ms.
- Because hop = 100 ms, the **maximum precision of an integrated reading is 100 ms**; a trailing partial block is dropped, not zero-padded.
- The mean square is over *samples within the block* (a rectangular window), not an exponential/IIR average. (The exponential moving averages some implementations use are the **Momentary (0.4 s) and Short-term (3 s)** measures of ITU-R BS.1771 / EBU Tech 3341 — see §6 and §3 — *not* the integrated measurement.)
- libebur128 implements this as `samples_in_100ms = (samplerate + 5) / 10`, `needed_frames = samples_in_100ms * 4` for the first block (400 ms), and uses one 100 ms step per update.

### 1.4 Channel weighting G

BS.1770-4, Table 3, *"Weightings for the individual audio channels"* (verbatim):

| Channel | Weighting, Gi |
|---|---|
| Left (GL) | 1.0 (0 dB) |
| Right (GR) | 1.0 (0 dB) |
| Centre (GC) | 1.0 (0 dB) |
| Left surround (GLs) | 1.41 (~ +1.5 dB) |
| Right surround (GRs) | 1.41 (~ +1.5 dB) |

> "The low frequency effects (LFE) channel is not included in the measurement."

(The LFE is excluded from the loudness measure. EBU Tech 3341 §2.10 adds: *"if the LFE channel were included in the loudness measurement it should be weighted by +10 dB"* — and that doing so is *no longer 'EBU Mode'*.)

### 1.5 Loudness, gating, and the gates — the exact chain

Per-block loudness, BS.1770-4 Eq. (4):

```
l_ij = −0.691 + 10 log10 Σ_i G_i · z_ij
```

Ungated loudness over interval T, BS.1770-4 Eq. (2), **verbatim**:

```
Loudness, LK = −0.691 + 10 log10 Σ_i G_i · z_i        LKFS
```

Gated loudness, BS.1770-4 Eq. (5), verbatim:

```
L_KG = −0.691 + 10 log10 ( (1/|Jg|) Σ_{j∈Jg} Σ_i G_i · z_ij )    LKFS
```

Gating indices, verbatim:

> "For a gating threshold Γ there is a set of gating block indices Jg = {j : lj > Γ} where the gating block loudness is above the gating threshold. The number of elements in Jg is |Jg|."

> "A two-stage process is used to make a gated measurement, first with an absolute threshold, then with a relative threshold. **The gating blocks below the absolute threshold are not used in the relative gating calculation.** The relative threshold Γr is calculated by measuring the loudness using the absolute threshold, Γa = −70 LKFS, and subtracting 10 from the result, thus:"

```
Γr = −0.691 + 10 log10 ( (1/|Jg|) Σ_{j∈Jg} Σ_i G_i · z_ij ) − 10   LKFS
where  Jg = { j : lj > Γa } ,  Γa = −70 LKFS                      (Eq. 6)
```

```
L_KG = −0.691 + 10 log10 ( (1/|Jg|) Σ_{j∈Jg} Σ_i G_i · z_ij )   LKFS
where  Jg = { j : lj > Γr and lj > Γa }                           (Eq. 7)
```

Applied exactly:

1. Compute every 400 ms block loudness `l_ij`/`l_j` (100 ms hop).
2. **Absolute gate:** keep blocks with `l_j > −70 LKFS`. (This alone is Eq. 2/5 with `Γa`.)
3. Compute the mean power of the survivors, convert to LUFS, **subtract 10 LU** → `Γr`.
4. **Relative gate:** keep blocks with `l_j > Γr` **and** `l_j > Γa`.
5. `L_KG` = `−0.691 + 10 log10` of the mean power of the doubly-gated blocks.

Note the trap: the relative threshold is derived from the *absolute-gated* mean, not from the ungated mean. And `|Jg|` in Eq. 6 is the count of absolute-gated blocks, in Eq. 7 the count of doubly-gated blocks.

### 1.6 The loudness-range gate chain (EBU Tech 3342) is different

Primary source: **EBU Tech 3342** (2023) *Loudness Range* — <https://tech.ebu.ch/docs/tech/tech3342.pdf>. Loudness Range (LRA) is **not** the integrated measurement; it uses a **−20 LU** relative gate:

> "The relative threshold is set to a level of **−20 LU** relative to the absolute-gated loudness level. … The absolute threshold is set to −70 LUFS, because no relevant signals are generally found below this loudness level."

> "The input to the algorithm is a vector of loudness levels, computed as specified in ITU-R BS.1770 with different relative-threshold gating, using a sliding analysis-window of length **3 seconds** for integration. … A minimum block overlap of 2.9 s between consecutive analysis windows (i.e. ≥10 Hz sampling of the loudness level) is required."

> "LRA is defined as the difference between the estimates of the **10th** and the **95th** percentiles of the distribution."

Reference constants, verbatim from the MATLAB listing in Tech 3342 §5:

```matlab
ABS_THRES = -70;     % LUFS   (= absolute measure)
REL_THRES = -20;     % LU     (= relative measure)
PRC_LOW   = 10;      % lower percentile
PRC_HIGH  = 95;      % upper percentile
```

**Stated difference:** integrated loudness (Programme Loudness) gates at **−10 LU** relative to the absolute-gated level over **400 ms** blocks; Loudness Range gates at **−20 LU** relative to the absolute-gated level over **3 s** windows and reports a 10th–95th percentile spread in **LU**. Do not reuse one gate chain for the other.

### 1.7 LU / LUFS / LKFS — same scale, different name

- BS.1770: *"The numerical result for the value of loudness that is calculated in equation (2) should be followed by the designation **LKFS**. This designation signifies: Loudness, K-weighted, relative to nominal full scale. The LKFS unit is **equivalent to a decibel** in that an increase in the level of a signal by 1 dB will cause the loudness reading to increase by 1 LKFS."*
- EBU R 128, footnote: *"'LUFS' is equivalent to 'LKFS' (which is used in ITU-R BS.1770). The EBU uses 'LUFS' which is compliant with international naming conventions."*
- EBU Tech 3341 §2.5: *"A relative measurement, such as relative to a reference level, or a range: LK = xx.x LU. An absolute measurement, LK = xx.x LUFS. The 'L' in 'LK' indicates loudness level, the 'K' indicates the frequency weighting used."*
- Tech 3341 §2.4: *"LRA is measured in units of 'LU'. It is noted that **1 LU is equivalent to 1 dB**."*

So `1 LU = 1 LUFS = 1 LKFS = 1 dB` in magnitude. **LU** is used for relative/ranges (e.g. gate thresholds in LU, LRA), **LUFS/LKFS** for absolute program loudness. The scale is the same; only the reference point differs.

### 1.8 The −0.691 constant and the 0 dBFS / 997 Hz reference

- BS.1770: *"If a 0 dB FS, 1 kHz (997 Hz to be exact, see Notes 1 and 2) sine wave is applied to the left, centre, or right channel input, the indicated loudness will equal **−3.01 LKFS**."*
- *"NOTE 1 – The constant −0.691 in equation (2) cancels out the K-weighting gain for 997 Hz."*
- *"NOTE 2 – IEC 61606 states that unless otherwise specified, the reference frequency for measurement shall be the actual frequency 997 Hz, which may be stated in non-critical contexts, as the nominal frequency 1 kHz."*

Derivation (arithmetic from the published equation, verified by measurement in §6): a sine of peak `A` has mean square `A²/2`; with K-gain `+0.6910 dB` at 997 Hz a **mono** 0 dBFS (A=1) sine gives `−0.691 + 10log10(0.5) + 0.691 = −3.01 LKFS`. For a **stereo, in-phase** sine of per-channel peak `p` dBFS, `Σ G_i z_i = A²` and the result collapses to exactly `p` LUFS — which is why EBU Tech 3341 test 1 (stereo 1 kHz at −23.0 dBFS peak, in phase) must read `−23.0 LUFS`.

- BS.1770 caveat: *"the algorithm is not, in general, suitable for use to estimate the subjective loudness of pure tones."*

## 2. True peak (BS.1770-4 Annex 2 / EBU Tech 3341)

Primary sources: **BS.1770-4 Annex 2** and **Attachment 1 to Annex 2**; **EBU Tech 3341 §2.6** — <https://tech.ebu.ch/docs/tech/tech3341.pdf>.

### 2.1 What true peak is, and why inter-sample peaks matter

> "True-peak level is **the maximum (positive or negative) value of the signal waveform in the continuous time domain**; this value may be higher than the largest sample value in the 48 kHz time-sampled domain." (BS.1770-4 Annex 2)

> "The problem occurs because the actual peak values of a sampled signal usually occur between the samples rather than precisely at a sampling instant, and as such are not correctly registered by the peak-sample meter." (Attachment 1)

Consequences quoted from Attachment 1: *"Inconsistent peak readings"*; *"Unexpected overloads: Since sampled signals may contain overloads even when they have no samples at, or even close to, digital full scale, overload indication by a peak-sample meter is unreliable."*; and *"for continuous pure tones it is easy to demonstrate, for example, a 3 dB under-read for an unfortunately-phased tone at a quarter of the sampling frequency. The under-read for a tone at half the sampling frequency could be almost infinite."*

This is exactly the case a normalizer must not miss: boosting a signal whose *sample* peak is below full scale can still clip on decode or on lossy re-encode.

### 2.2 The oversampling requirement and the specified filter

BS.1770-4 Annex 2, verbatim stage list:

> "The stages of processing are:
> 1 Attenuate: 12.04 dB attenuation
> 2 4 × over-sampling
> 3 Low-pass filter
> 4 Absolute: Absolute value
> 5 Conversion to dB TP"

> "The first step consists of imposing an attenuation of 12.04 dB (2-bit shift). The purpose of this step is to provide headroom for the subsequent signal processing that could employ integer arithmetic. **This step is not necessary if the calculations are performed in floating point.**"

> "The 4 × over-sampling filter increases the sampling rate of the signal from 48 kHz to **192 kHz**. … **Higher sampling rates and over-sampling ratios are preferred**. Incoming signals that are at higher sampling rates require proportionately less over-sampling (e.g. for an incoming signal at 96 kHz sample rate a 2 × over-sampling would be sufficient.)"

The document then gives **one set** of coefficients "for the order 48, 4-phase, FIR interpolating" filter (Table, Annex 2), e.g. Phase 0 begins `0.0017089843750 / 0.0109863281250 / −0.0196533203125 / 0.0332031250000 / −0.0594482421875 / 0.1373291015625 / 0.9721679687500` and is symmetric. So: **4× minimum, order-48 4-phase FIR is the example that satisfies it.**

**Under-read budget.** Attachment 1 gives the closed form and a table:

> "maximum under-read (in dB) = 20.log(cos(π.fnorm/n))"

| Over-sampling ratio n | Under-read dB, fnorm = 0.45 | Under-read dB, fnorm = 0.5 |
|---|---|---|
| 4 | 0.554 | 0.688 |
| 8 | 0.136 | 0.169 |
| 12 | 0.060 | 0.075 |
| 16 | 0.034 | 0.042 |

So **4× alone admits up to ~0.55 dB under-read at 21.6 kHz (fnorm 0.45, where `fnorm = f/fs` — so fnorm 0.5 is Nyquist)**; 8× buys ~0.14 dB. If you want better than the EBU tolerance below, use ≥8×.

### 2.3 dBTP definition

> "Meters that follow these guidelines, and that use an oversampled sampling rate of **at least 192 kHz**, should indicate the result in the units of **dB TP** … This can be achieved by calculating "20log10" of the attenuated, oversampled, filtered, absolute value, then adding 12.04 dB. The "dB TP" designation signifies **decibels relative to 100% full scale, true-peak measurement**."

EBU R 128 definitions section: *"Maximum True Peak Level: The maximum value of the audio signal waveform of a programme in the continuous time domain."*

### 2.4 What a compliant meter must show, tolerances, and the ceiling

**EBU R 128, verbatim:** *"the True Peak Level of a programme **shall not exceed −1 dBTP** (dB True Peak) during production (linear audio), measured with a meter compliant with ITU-R BS.1770 and EBU Tech 3341. **The measurement tolerance is ±0.3 dB** (for signals with a bandwidth limited to 20 kHz). Permitted Maximum True Peak Levels may be lower for different distribution systems and data reduction rates."*

**EBU Tech 3341 §2.6:** *"In addition to the specifications of ITU-R BS.1770 Annex 2, the true-peak measure implemented in an 'EBU Mode' meter shall comply with the tolerances specified in Table 1 (signals 15-23), intended as 'minimum requirements' tests. The total measurement error of the true-peak level must comply with these tests, including any pass-band ripple in the upsampling filter and the 'under-read' described in ITU-R BS.1770, Appendix 1 to Annex 2."*

Tech 3341 Table 1 true-peak cases (verbatim extract), all *"Max. true-peak level = −6.0 **+0.2/−0.4** dBTP"* unless noted:

| # | Signal | Expected |
|---|---|---|
| 15 | Stereo sine `fs/4`, amplitude 0.50 FFS, phase 0.0°, 10 ms tapers | −6.0 +0.2/−0.4 dBTP |
| 16 | `fs/4`, 0.50 FFS, phase 45.0° | −6.0 +0.2/−0.4 dBTP |
| 17 | `fs/6`, 0.50 FFS, phase 60.0° | −6.0 +0.2/−0.4 dBTP |
| 18 | `fs/8`, 0.50 FFS, phase 67.5° | −6.0 +0.2/−0.4 dBTP |
| 19 | `fs/4`, amplitude **1.41** FFS, phase 45.0° | **+3.0** +0.2/−0.4 dBTP |
| 20–23 | `fs/6` carrier containing one period of `fs/4` at amplitude 1.00, synthesised at 4·fs then low-pass filtered and down-sampled at 0/1/2/3-sample offsets | **0.0** +0.2/−0.4 dBTP |

So the **true-peak acceptance band is +0.2 / −0.4 dBTP** per test signal — the meter may over-read by 0.2 dB and must not under-read by more than 0.4 dB. `fs` here means the actual sample rate (12 kHz at 48 kHz).

## 3. EBU R128 and streaming targets

### 3.1 EBU R 128 — the target and exact wording

Primary source: **EBU R 128** (2023, V5) — <https://tech.ebu.ch/docs/r/r128.pdf>.

Verbatim (2023 text):

> "that the Programme Loudness Level shall be normalised to a **Target Level of −23.0 LUFS**. Where attaining the Target Level is not achievable practically (for example, live programmes), a **tolerance of ±1.0 LU** is permitted. A broadcaster should ensure that a deviation from the Target Level towards the limits of the tolerance does not become standard practice;"

> "that for the implementation of Loudness workflows (for example, in Quality Control environments) a **tolerance of ±0.2 LU** is allowed in order to take account of measurement errors;"

> "that the measurement shall be made with a loudness meter compliant with ITU-R BS.1770 (including the level-gating method described in equation (7)) and EBU Tech 3341;"

Document history (verbatim), which is where the familiar **±0.5 LU** figure comes from:

> "June 2014 V3; Target level (−23 LUFS) tolerance changed to **± 0.5 LU (except Live-programmes)**"
> "August 2020 V4; Tolerances updates and references to R 128 s1 and s2 added"
> "November 2023 V5; References to R 128 s3, s4 and Tech 3401 added"

**Read this precisely:** the *current* R 128 (2023) normative text states −23.0 LUFS with ±1.0 LU for live/impractical cases and ±0.2 LU for QC workflows. The often-quoted "±0.5 LU" is the V3 (June 2014) revision recorded in the document history. R 128 never states "±0.5 LU" in its 2023 body.

Other R 128 facts: LRA §(*n*), max momentary/short-term §(*o*), and the streaming supplement referenced as *"EBU R 128 s2 'Loudness in Streaming'"*.

### 3.2 Targets actually used by platforms

**Rule of thumb that governs the design:** several platforms **only attenuate** (never boost). For a normalizer extension this is decisive — a tab whose audio is below the platform target is often left quiet, so *raising* quiet tabs is a real gain in user experience and cannot be delegated to the platform.

Spotify is the only major music platform that publishes a full, numeric, bidirectional gain policy. Its own text is worth quoting in full because it encodes the exact headroom rule a normalizer must respect:

> "**Negative gain** is applied to louder masters so the loudness level is −14 dB LUFS. This lowers the volume in comparison to the master - no additional distortion occurs.
> **Positive gain** is applied to softer masters so the loudness level is −14 dB LUFS. **We consider the headroom of the track, and leave 1 dB headroom for lossy encodings to preserve audio quality.**
> Example: If a track loudness level is −20 dB LUFS, and its True Peak maximum is −5 dB FS, **we only lift the track up to −16 dB LUFS**."

> "**Loud**: −11 dB LUFS. Note: We set this level regardless of maximum True Peak. **We apply a limiter** to prevent distortion and clipping in soft dynamic tracks. The limiter's set to engage at **−1 dB (sample values), with a 5 ms attack time and a 100 ms decay time**."

Design translation: **gain = target − measured, capped so that `peak + gain ≤ ceiling`** (Spotify: 1 dB remaining headroom below full scale). This is the same shape as ReplayGain's clipping-prevention formula in §3.3.

### 3.3 ReplayGain 2.0 — the actual specification

The canonical spec lives at `wiki.hydrogenaud.io`, which returns **HTTP 403** to a plain client (it blocks non-browser user agents). The free primary access used here is the Wayback Machine capture of the same page (permanent link in the capture): <https://web.archive.org/web/20241225200927/https://wiki.hydrogenaud.io/index.php?title=ReplayGain_2.0_specification> (capture of revision `oldid=37213`, page last edited 2023-08-07).

**What filter does RG2 use?** Not its own. Verbatim:

> "RG2 uses **BS.1770-3** for loudness measurement. It is expected the ITU standard will evolve over time to meet the needs of broadcasters and governments. It is the intent of the ReplayGain community that RG2 follow any future backwards-compatible improvements to loudness measurement using the BS.1770 standard."

> "Since original ReplayGain proposal in 2001, the science, practice and standards for loudness normalization have been advanced significantly. … BS.1770-3 uses a "K-weighted" RMS measurement. This weighting function is significantly less complex than the inverted Fletcher-Munson weighting used by RG1. … RG2 uses BS.1770-3 for loudness measurement. … The computation required for BS.1770-3 loudness measurement is reduced compared to the RG1 technique."

So **RG2 has no proprietary filter**: use §1 here (K-weighting). (RG1 did define its own — an inverse equal-loudness IIR; the RG2 spec describes RG1 only qualitatively as "a loudness measurement system which included a weighting filter, root mean square (RMS) measurement and statistical processing that model human perception of loudness in both the frequency and time domains".)

**Reference level, verbatim:**

> "In order to maintain backwards compatibility with RG1, RG2 uses a **−18 LUFS reference**, which based on lots of music, can give similar loudness compared to RG1."

> "RG1 is calibrated to a pink noise reference signal with a RMS level 14 dB below a full-scale sinusoid."

**Gain, verbatim:** `RG = L_r − L`, where `L_r` = −18 LUFS reference and `L` = measured loudness in LUFS. *"Replay gain is positive if the loudness of the audio file is lower than the reference level. The gain is negative (representing an attenuation) if the loudness of the audio file is higher than the reference level."*

**Track vs album gain, verbatim:** *"If calculated for an individual track, the loudness measurement (as specified above) yields track replay gain. If calculated on an album basis, with all tracks concatenated to make one long audio file, the loudness measurement yields album replay gain."* Both are stored, so a player can choose *"Track style level normalization (all tracks same loudness)"* or *"Album style level normalization (all albums same loudness, tracks of an album played at the same relative level as on the original release)"*.

**Playing back (the scalar), verbatim:** *"Scaling the audio data simply means multiplying each sample value by a constant value. This constant is given by: `10^(gain/20)`."*

**Clipping prevention, verbatim:** two options — *"Audio limiting"* (hard limit just below full scale) or *"Reduced gain"* (automatically reduce pre-amp gain where clipping would occur, predicted from stored peak metadata). The combined scale factor, verbatim:

```
min( 10^((RG + G_pre-amp)/20) , 1 / peak_amplitude )
```

> "The player must read the peak amplitude metadata. **If peak level metadata is unavailable, the player should assume a peak level of 1.0.**"

**Metadata keys** (verbatim table): `REPLAYGAIN_TRACK_GAIN` `[-]a.bb dB`, `REPLAYGAIN_TRACK_PEAK` `c.dddddd` (1.000000 = full scale), `REPLAYGAIN_ALBUM_GAIN`, `REPLAYGAIN_ALBUM_PEAK`; de-facto extensions `REPLAYGAIN_TRACK_RANGE`/`_ALBUM_RANGE` (LRA in dB/LU) and `REPLAYGAIN_REFERENCE_LOUDNESS`.

Note: RG2's clipping prevention uses **sample peak**, not true peak (the spec stores the maximum absolute sample value). A modern normalizer should store/compare **true peak** instead (§2).

## 4. Dynamic range compression done right (the "night mode" part)

### 4.1 Why naive per-sample or fast AGC pumps and distorts

A gain that follows the *instantaneous* sample magnitude is a rectifier + gain, i.e. a multiplier whose value is a function of the signal — this is amplitude modulation, which creates intermodulation distortion, and a gain that moves within the duration of a low-frequency cycle generates audible *harmonic* content from that cycle. A gain that follows the *envelope with too short an attack/release* produces audible **pumping** (loud passages duck the following quiet passage) and **breathing** (the noise floor rises and falls).

The published controls that avoid this are the classic compressor parameters, and the *primary documentation of their meaning* is the Web Audio spec (§4.3) and the Dolby DRC profiles (§4.4). A correct downward compressor has: **threshold, ratio, knee (soft), attack, release, makeup gain**, with attack/release necessarily ≫ 1/F_min.

No DSP textbook is quoted here because none is needed: the compressor *is* described normatively by Web Audio (`DynamicsCompressorNode`) and by vendor DRC profiles, both of which are primary for the values given.

### 4.2 Threshold, ratio, knee, attack, release, makeup — the recommended ranges

There are two *published, quotable* parameter sets for a perceptual compressor. Use one of these rather than inventing numbers.

1. **Web Audio `DynamicsCompressorNode` defaults** (§4.3): threshold −24 dB, knee 30 dB, ratio 12:1, attack 3 ms, release 250 ms. These are the defaults a browser ships, and the attack/release (3 ms / 250 ms) are the concrete "don't pump" numbers.
2. **Dolby "Film Standard" DRC profile** (§4.4): max boost 6 dB below −43 dB, 2:1 boost 43→31 dB, a **5 dB null band** 31→26 dB, 2:1 early cut −26→−16 dB, **20:1 cut** −16→+4 dB. This is the canonical "night mode" shape: nothing happens in a 5 dB window around dialogue level, gentle 2:1 at the edges, hard 20:1 limiting of loud peaks.

For **speech intelligibility without squashing music**, the published design intent is the Dolby null-band approach: pick the threshold at the *dialogue anchor level* and leave a **null band** of ~5 dB around it so that ordinary program material is untouched, then compress with 2:1 outside the band and limit with ~20:1 at the top. That is exactly what Apple's and Microsoft's consumer controls implement (§4.4).

**Attack/release guidance derived from the published values:** attack in the low single-digit milliseconds (3 ms per Web Audio default) is fast enough to catch transients but is *not* per-sample; release of 100–350 ms (Web Audio default 250 ms; Spotify's Loud-mode limiter 5 ms attack / 100 ms decay; Dolby RF-mode profiles are "more restrictive") keeps the gain out of the audio band. Anything under ~1 ms attack or under ~10 ms release is a limiter, not a compressor, and belongs after the gain stage, not in the loudness estimate.

### 4.3 "Normalize loudness" vs "compress dynamics" — and why riding gain fast is wrong

- **Loudness normalization** = one static gain per program, `gain = target − measured integrated loudness`, applied as a constant multiplier, bounded by the peak/true-peak ceiling. It preserves the program's internal dynamics exactly. This is EBU R 128, ReplayGain, and every streaming platform (§3).
- **Dynamic range compression** = a *time-varying* gain that deliberately reduces the program's loudness range (LRA). It changes the internal dynamics by design; it is a creative/accessibility transform, not a normalizer.

A normalizer that "rides gain fast" is neither: it recomputes a gain from a short window and applies it continuously, which *is* compression/AGC, and because the estimate lags the signal it both **pumps** and **mis-measures** (the 400 ms block structure of §1.3 means a fast gain changes the very signal you are measuring). The correct split is:

1. Measure integrated loudness on the **unmodified** signal with the §1.3 block structure (400 ms, 75 % overlap, both gates).
2. Convert to **one static gain**, rate-limited over seconds (not per 100 ms block), bounded by the ceiling rule of §3.2/§3.3.
3. If (and only if) the user asked for "night mode", run a **separate, correct compressor** with the §4.2 parameters, *after* the static gain.

## 5. Real-time implementation in the browser

### 5.1 `AudioWorkletProcessor.process()` contract, render quantum, real-time constraints

Primary source: **W3C Web Audio API** — <https://webaudio.github.io/web-audio-api/> (also <https://www.w3.org/TR/webaudio/>).

**Process contract, verbatim:**

> "Users can define a custom audio processor by extending AudioWorkletProcessor. The subclass **MUST define an AudioWorkletProcessCallback named `process()`** that implements the audio processing algorithm and may have a static property named `parameterDescriptors` … The `process()` callback function is handled as specified when rendering a graph."

Callback signature, verbatim IDL:

```webidl
callback AudioWorkletProcessCallback =
  boolean (FrozenArray<FrozenArray<Float32Array>> inputs,
           FrozenArray<FrozenArray<Float32Array>> outputs,
           object parameters);
```

> "The return value of this callback controls the lifetime of the AudioWorkletProcessor's associated AudioWorkletNode." … "Nodes that transform their inputs, and are active only while connected inputs and/or script references exist. Such nodes SHOULD return **false** from `process()`…" … "Nodes that transform their inputs, but which remain active for a tail-time after their inputs are disconnected … process() SHOULD return **true** for some period of time after inputs is found to contain zero channels."

> "If there are no actively processing AudioNodes connected to the nth input … then the content of `inputs[n]` is an **empty array**, indicating that zero channels of input are available. **This is the only circumstance under which the number of elements of `inputs[n]` can be zero.**"

> "`outputs[n][m]` is a Float32Array object containing the audio samples for mth channel of nth output. **Each of the Float32Arrays are zero-filled.**"

**Render quantum, verbatim:**

> "The AudioContext's render quantum size is the **default value of 128 frames**." (enum `AudioContextRenderSizeCategory` `"default"`; `"hardware"` = "The User-Agent picks a render quantum size that is best for the current configuration.")

Note the spec now also exposes `readonly attribute unsigned long renderQuantumSize;` on `BaseAudioContext` (newer revision). For a normalizer, do **not** hard-code 128: read `renderQuantumSize` if present, and never assume `output[0].length` is constant across calls.

**Allocation / GC / lock constraints, verbatim:**

> "In general, the `inputs` and `outputs` arrays **will be reused between calls so that no memory allocation is done**. However, if the topology changes, because, say, the number of channels in the input or the output changes, **new arrays are reallocated**. New arrays are also reallocated if any part of the inputs or outputs arrays are transferred."

> "This frozen ordered map … **the object cannot be modified** and hence the same object can be used for successive calls unless length of an array changes."

These are the spec's own statements that `process()` runs on the audio rendering thread and that **you must not allocate**: the arrays are reused precisely so that the implementation does no allocation per quantum. Practical rules that follow (and which are the same rules any real-time audio callback obeys):

- Allocate every `Float32Array` (delay lines, analysis buffers, coefficient tables) in the **constructor** or in a `port.onmessage` handler, never inside `process()`.
- No `new`, no array/object literals, no closures, no `push`/`slice`/`map` inside `process()`.
- No `console.log`, no `postMessage` per quantum (throttle: accumulate and post every N quanta).
- No locks/mutexes and no synchronous I/O: `SharedArrayBuffer` + `Atomics` is the only wait-free channel, and the *audio* thread must never block on it. Message passing via `port` is asynchronous and safe.
- Measure with `renderQuantumSize = 128` at 48 kHz → the callback budget is `128/48000 ≈ 2.67 ms`; at 44.1 kHz `≈ 2.90 ms`.

**Why `ScriptProcessorNode` is unusable here.** The spec labels it deprecated:

- Section title: *"The ScriptProcessorNode Interface - DEPRECATED"*.
- *"There are also several features that have been deprecated from the Web Audio API but not yet removed, pending implementation experience of their replacements: A ScriptProcessorNode interface, an AudioNode for generating or processing audio directly using scripts."*
- *"This is an Event object which is dispatched to ScriptProcessorNode nodes. **It will be removed when the ScriptProcessorNode is removed, as the replacement AudioWorkletNode uses a different approach.**"*
- It runs on the **main thread** (the spec lists it under "Audio Buffer Copying" / control-vs-rendering thread buffering: *"The ScriptProcessorNode can have buffers between the control thread and the rendering thread."*), so any GC pause or layout in the page produces a dropout, and its fixed buffer size adds latency.

Use `AudioWorkletNode` (or, where the node graph suffices, built-in nodes).

### 5.2 `AudioParam` a-rate vs k-rate and smoothing gain

Verbatim:

> "…an `AudioParam` … **a-rate parameter which means that its values MUST be taken into account on a per-audio-sample basis**, or it is a **k-rate** … the value of a k-rate parameter MUST be sampled at the time of the [render quantum] block. a-rate parameters MUST be sampled for [each sample]."

> "The automation rate of an AudioParam can be selected setting the `automationRate` …" — `"a-rate"` = "This AudioParam is set for a-rate processing."; `"k-rate"` = "This AudioParam is set for k-rate processing."

Automation-rate constraints, verbatim: *"Some nodes have additional automation rate constraints as follows: … `DynamicsCompressorNode` `threshold`, `knee`, `attack`, and `release` MUST be `k-rate`. An `InvalidStateError` [is thrown if set to] `"a-rate"`."*

**Getting this right for a normalizer:**

- Use **`GainNode.gain` (a-rate)** for the loudness gain and the limiter gain, driven by `setTargetAtTime`/`linearRampToValueAtTime` or by scheduling a per-quantum ramp. That is what prevents **zipper noise** (stepped gain changes once per 128-sample block produce a 375 Hz buzz at 48 kHz — audible).
- If you keep the gain inside your own `AudioWorkletProcessor`, interpolate it **per sample across the quantum**: compute `gainStep = 10^((dB_end − dB_start)/20)^(1/N)` once per quantum and multiply into the loop (a geometric ramp), or `gain += delta / N` (a linear ramp). Both are O(1) extra work per quantum and remove zipper noise.
- `threshold/knee/ratio/attack/release` on `DynamicsCompressorNode` are k-rate by constraint — you cannot smooth them per-sample, so **do not automate them for a normalizer**.
- The spec's `parameters["name"]` array is length N (per-frame values) *or* length 1 when nothing is automated: *"if no automation is scheduled during this render quantum, the array MAY have length 1 with the array element being the constant value of the AudioParam for the render quantum."* Handle both.

### 5.3 Latency budget and true-peak lookahead

A true-peak limiter cannot react to a peak it has not seen yet, so it needs **lookahead** and therefore **adds latency** equal to the lookahead. Primary evidence that browsers themselves accept this:

- Web Audio spec, on processing latency: *"The **DynamicsCompressorNode has a look ahead algorithm that causes delay in the signal path.**"* — <https://webaudio.github.io/web-audio-api/> (§7.1)
- The same section lists `ConvolverNode`, `BiquadFilterNode`/`IIRFilterNode`, `WaveShaperNode` (when oversampling) as adding delay — relevant if you oversample for true-peak detection inside the worklet.

Budget:

- **Lookahead must be ≥ the attack ramp.** The worklet's `LOOKAHEAD_SECONDS` and `LIMITER_ATTACK_SECONDS` feed `this.delayFrames = Math.max(128, Math.round(sr * LOOKAHEAD_SECONDS))` and `this.limiterAttackFrames = Math.max(1, Math.round(sr * LIMITER_ATTACK_SECONDS))` in `constructor()` → **240 and 96 frames at 48 kHz**. `scheduleLimiter()` writes the ramp *backwards* from the write pointer, so it has to fit inside the delay window: 96 ≤ 240 holds.
- **Total latency added by the worklet is exactly `this.delayFrames`, nothing else.** `process()` emits `this.channelBuffers[ch][readIndex]` with `readIndex = this.writeIndex + this.bufferLength - this.delayFrames` → **240 frames = 5.000 ms at 48 kHz**. At 44.1 kHz the same expression gives `Math.round(220.5) = 221` frames = **5.011 ms** (JavaScript's `Math.round` rounds half towards +∞). The `Math.max(128, …)` floor only binds below sr = 25 600 Hz, where the lookahead is capped: 5.805 ms at 22.05 kHz, 8.000 ms at 16 kHz.
- **The 4× true-peak oversampler contributes 0 ms to that total.** Its FIR runs on a private history ring — `this.interpZ`, one `Float64Array(25)` per channel — fed from the *undelayed* sample (`interpPeak()` is called on `this.preScratch` before that sample is written to `this.channelBuffers`); its result drives only the limiter decision, and the reported telemetry comes from a separate `outputPeak()` history (`this.outInterpZ`, also `Float64Array(25)`) fed from the delayed post-limiter output, and the audio in the delay line never passes through the interpolator. `this.interpDelay = 25` is a **buffer size, not a delay** — it is `(taps + factor - 1) / factor = (97 + 4 - 1) / 4 = 25`, the maximum taps per phase (libebur128's equivalent with 49 taps is 13). For the record, the interpolator's own group delay is `(taps - 1) / 2 = 48` sub-samples at 4× = **12 input samples ≈ 0.25 ms at 48 kHz**, which describes *where the peak estimate is centred*, not a delay added to the output; it is 20× smaller than the 5 ms lookahead that already covers it. (Detector *accuracy* is a §2 question, not a latency one: the 4× under-read bound of §2.2 is 0.688 dB at Nyquist, against a `TP_DETECTOR_MARGIN_DB` that the worklet sets — 1.0 dB, sized from the measured worst-case end-to-end under-read of 0.51 dB against the ffmpeg oracle.)
- Total pipeline latency to disclose/compensate: `capture jitter + worklet delay + output device latency`. Keep the loudness path at **zero** added latency (static gain, no lookahead) and put the lookahead only in the true-peak limiter.
- Do not run the BS.1770 measurement on the *output* of a lookahead limiter without accounting for the delay, or the measurement will be time-shifted relative to the audio.

### 5.4 `DynamicsCompressorNode` — documented parameters and documented limits

Interface, verbatim:

```webidl
interface DynamicsCompressorNode : AudioNode {
  constructor(BaseAudioContext context, optional DynamicsCompressorOptions options = {});
  readonly attribute AudioParam threshold;
  readonly attribute AudioParam knee;
  readonly attribute AudioParam ratio;
  readonly attribute float reduction;
  readonly attribute AudioParam attack;
  readonly attribute AudioParam release;
};
```

Documented parameters (verbatim descriptions and defaults):

| Attribute | Spec description | default | min | max | rate |
|---|---|---|---|---|---|
| `threshold` | "The decibel value above which the compression will start taking effect." | `−24` | `−100` | `0` | k-rate |
| `knee` | "A decibel value representing the range above the threshold where the curve smoothly transitions to the "ratio" portion." | `30` | `0` | `40` | k-rate |
| `ratio` | "The amount of dB change in input for a 1 dB change in output." | `12` | `1` | `20` | k-rate |
| `attack` | "The amount of time (in seconds) to reduce the gain by 10dB." | `.003` | `0` | `1` | k-rate |
| `release` | "The amount of time (in seconds) to increase the gain by 10dB." | `.25` | `0` | `1` | k-rate |
| `reduction` | "A read-only decibel value for metering purposes, representing the current amount of gain reduction that the compressor is applying to the signal. If fed no signal the value will be 0 (no gain reduction)." | — | — | — | float |

**Is it suitable as the compressor?** Partly, and with named limits:

- **Suitable** for the §4.4 "night mode" compressor: it is a genuine wideband downward compressor with a soft knee, a metering output (`reduction`), documented attack/release, and the defaults (3 ms attack / 250 ms release) are in the right range.
- **Not suitable** as the loudness *normalizer*: it is a compressor, not a static-gain normalizer. Feeding the gain through it changes the program's LRA, which is a different operation (§4.3) and violates a normalizer's "preserve dynamics" contract.
- **Documented limitations:** (a) its detector curve and its exact gain-computer algorithm are **not specified** by the standard — only the five parameters and their meanings are; implementations differ across browsers, so it is not reproducible against a reference; (b) all five parameters are **k-rate with constraints** and cannot be automated per sample; (c) it adds **look-ahead latency** (*"has a look ahead algorithm that causes delay in the signal path"*) and has tail-time; (d) it exposes **no input/output gain or makeup-gain** and no lookahead control; (e) `reduction` is read-only and read from the **control** thread, so it cannot be used for closed-loop normalisation inside the audio graph.

Verdict: use `DynamicsCompressorNode` only for the optional night-mode stage; implement loudness measurement and the static gain yourself (§1, §5.2).

> "**If an `AudioContext` is created before the document receives a user gesture, it will be created in the 'suspended' state, and you will need to call `resume()` after the user gesture.**"

This aligns with tabCapture's user-gesture requirement: the same click that starts capture can resume the context. Inside an extension page the gesture chain is the toolbar click; inside a content script on an arbitrary page, do not assume a gesture exists.

**`HTMLMediaElement.captureStream()`** — MDN/spec: <https://developer.mozilla.org/en-US/docs/Web/API/HTMLMediaElement/captureStream>, specification link *"Media Capture from DOM Elements § dom-htmlmediaelement-capturestream"* (<https://w3c.github.io/mediacapture-fromelement/>). MDN verbatim: *"returns a MediaStream object that streams a real-time capture of the content being rendered in the media element."* It is **not universally supported** (MDN: *"This feature is not Baseline because it does not work in some of the most widely-used browsers"*) and, more importantly, it only sees audio the page already has as a media element — it does not help for `<audio>`-less playback, Web Audio sinks, or other tabs. It is also subject to the element's own CORS/track state.

**What cannot be captured at all:**

- **DRM / Widevine-protected audio.** Chrome renders protected media through a path that is not exposed to page- or extension-level capture; a captured protected tab yields no usable audio. Chrome's public extension documentation does not state this, so the closest primary is the Chromium issue tracker, *"Google chrome widevine screen recording"*: <https://issues.chromium.org/issues/326321538>, and Google's own help-forum report that Widevine content produces a *black screen* / no capture on Windows: <https://support.google.com/chrome/thread/161292567>. **Treat as a hard limitation:** do not promise to normalize Spotify/Netflix/Prime DRM playback. (Radio/music in a normal tab is usually not DRM-protected.)
- **Cross-origin audio inside another tab** is captured only as tab *output* (mix), not as separate streams, and audio from **other extensions**, from **privileged UI** (chrome:// pages, the New Tab page, extension pages you don't own), and from **other tabs** cannot be captured by `tabCapture` at all — it captures one tab.
- **OS-level audio** (other applications, system sounds, the OS mixer) is outside `tabCapture`; it needs `getDisplayMedia`/`desktopCapture` and, on some platforms, a system-audio loopback that Chromium does not provide.
- **Silence while muted/suspended**: when the capture `AudioContext` is suspended by autoplay policy, the stream produces no audio and the normalizer will measure silence — gate on `context.state`.

### 5.6 Clock / sample rate: 48 000 vs 44 100

`AudioContext.sampleRate` is the hardware rate and is commonly **48000** but is **44100** on machines whose audio device runs at 44.1 kHz. It is a `readonly attribute float sampleRate;` on `BaseAudioContext` (Web Audio spec). No primary source mandates which; the spec only requires that `sampleRate` reflects the context.

**How a BS.1770 implementation must handle both:** the K-weighting coefficients in BS.1770 are **only valid at 48 kHz**, and the standard says so explicitly — *"These filter coefficients are for a sampling rate of 48 kHz. Implementations at other sampling rates will require different coefficient values."* Therefore:

1. Prefer to **run the measurement in a context at 48 kHz** (`new AudioContext({ sampleRate: 48000 })`), which the Web Audio spec allows, and resample the captured stream via `MediaStreamAudioSourceNode` (the UA resamples). This makes the published coefficients exactly correct and avoids a second coefficient set.
2. If you must run at the hardware rate, **redesign the two biquads** with the published design parameters (libebur128's `f0/G/Q`, quoted in §1.2) evaluated at that rate. The verified 44.1 kHz coefficients are given in §1.2.
3. Use the **same** rate for measurement and for the gain scheduling; a mismatch silently mis-scales the 400 ms block.

For the SSL suite of EBU test signals the reference rate is 48 kHz: *"These 'minimum requirements test signals' are available for download from the EBU Technical website, **synthesized at a sampling rate of 48 kHz**."* (Tech 3341 §2.9.)

True peak: BS.1770's 4× example goes 48 → 192 kHz; at 44.1 kHz the same 4× goes to 176.4 kHz, and the under-read table is a function of `fnorm = f/fs`, so the *same* ratios give the same under-read. libebur128 chooses the oversampling factor by absolute rate (`interp_create(49, 4, ch)` for fs < 96 kHz, `interp_create(49, 2, ch)` for fs < 192 kHz, none above).

### 6.2 Test signals that actually discriminate

All measurements below were run locally on this machine with `ffmpeg 9.0.2` and `ebur128=framelog=quiet:peak=true`. Signals were generated as exact float32 raw (`-f f32le -ar 48000 -ac 2`) by a small Python script, and by `aevalsrc`.

**(a) Analytically-known case — stereo 1 kHz in phase, per-channel peak −23 dBFS, 20 s.**

Expected: `I = −23.0 LUFS` exactly (derivation in §1.8; this is EBU Tech 3341 test 1). Measured:

```
Integrated loudness:
I:         -23.0 LUFS
Threshold: -33.0 LUFS
True peak:
Peak:      -23.0 dBFS
```

Same at −33 dBFS per channel → measured `I: -33.0 LUFS`. ✓

**(b) Analytically-known case — mono 997 Hz at 0 dBFS peak, 20 s.** BS.1770 requires `−3.01 LKFS`. Measured: `I: -3.0 LUFS`, `Peak: 0.0 dBFS`. ✓ (The mono/stereo 3.01 dB step is the difference between `Σ G_i z_i = A²/2` and `= A²`.)

**(c) Gated-silence cases (prove both gates work).** These are EBU Tech 3341 Table 1 tests 3, 4, 5. If gating is absent, the results are *lower* than −23.0; if only the −70 dBFS absolute gate is present, tests 4/5 fail; if the −10 LU relative gate is broken, tests 3/4/5 fail. All three must read **`−23.0 ± 0.1 LUFS`**:

| Test (Tech 3341 #) | Signal (stereo 1 kHz, per-channel peak) | Measured I | Measured threshold | LRA |
|---|---|---|---|---|
| 3 | 10 s @ −36, 60 s @ −23, 10 s @ −36 | **−23.0 LUFS** | −34.2 LUFS | 13.0 LU |
| 4 | 10 s @ −72, 10 s @ −36, 60 s @ −23, 10 s @ −36, 10 s @ −72 | **−23.0 LUFS** | −34.2 LUFS | 13.0 LU |
| 5 | 20 s @ −26, 20.1 s @ −20, 20 s @ −26 | **−23.0 LUFS** | −33.0 LUFS | 6.0 LU |

The measured `Threshold` line is the reference implementation telling you which relative gate it used: for test 3/4 it is −34.2 (= −23.0 − 11.2, i.e. it gated at the −70 LUFS absolute-gated level minus 10 LU, and the −36/−72 segments fell out); for test 5 it is exactly −33.0 (= −23.0 − 10). A correct implementation reproduces both.

**(d) A quiet passage that must NOT be measured.** Same as test 3/4 above: the −36 dBFS and −72 dBFS segments are 13 LU and 49 LU below the program, so both gates exclude them. **Discriminator:** compute the ungated mean of the test-3 signal and you get ≈ **−25.5 LUFS**, which is *wrong*; only the gated value −23.0 is correct. Any implementation that returns ≈−25.5 on test 3 has a broken gate.

**(e) Channel weighting (proves G ≠ 1 for surrounds).** EBU Tech 3341 test 6: 5.0-channel 1 kHz sine, 20 s, per-channel peaks L,R = −28 dBFS, C = −24 dBFS, Ls, Rs = −30 dBFS → expected `I = −23.0 ±0.1 LUFS`. Measured: **−23.0 LUFS**. With surround weighting G wrongly set to 1.0 the result is ≈ −23.6 LUFS. This test is the only one that isolates Table 3.

**(f) Pink noise.** `anoisesrc=color=pink:amplitude=0.5:sample_rate=48000`, 20 s → measured `I: -20.6 LUFS`, `LRA: 0.1 LU`, `Peak: -7.2 dBFS`. Pink noise has no closed-form LUFS value, but it is a stable cross-implementation check and it exercises the low-frequency part of the RLB high-pass. Use it as a two-implementation agreement test, not as an absolute truth.

**(g) A signal that clips on inter-sample peaks.** EBU Tech 3341 tests 15–23. Two concrete runs (verbatim from Tech 3341: taper the tone with a 10 ms fade in/out):

```
# 12 kHz (= fs/4) sine, amplitude 0.50 FFS, phase 0 — must read -6.0 +0.2/-0.4 dBTP
ffmpeg -f lavfi -t 5 -i "aevalsrc=0.5*sin(2*PI*12000*t)|0.5*sin(2*PI*12000*t):s=48000" \
  -af "afade=t=in:st=0:d=0.01,afade=t=out:st=4.99:d=0.01,ebur128=framelog=quiet:peak=sample+true" -f null -
```

Measured:

```
Sample peak:  Peak: -6.0 dBFS
True peak:    Peak: -6.0 dBFS
```

**Without the 10 ms taper the same signal reads `TPK: -5.6 dBFS`** (a 0.4 dB over-read caused by the truncated end ringing through the interpolation filter) — which is why Tech 3341 specifies the taper and why an untapered test can produce a *false failure*. This is the practical trap in true-peak testing.

The discriminating frame-level log (same signal, `framelog=info`, `peak=sample+true`) shows the difference directly:

```
... SPK:  -6.0  -6.0 dBFS   FTPK:  -6.0  -6.0 dBFS   TPK:  -5.6  -5.6 dBFS
```

i.e. **sample peak −6.0 vs true peak −5.6** on the untapered signal — exactly the inter-sample-error the measure exists to catch.

**(h) Amount of attenuation / the reference for `dBTP`.** With a 4× oversampler the maximum under-read at fnorm 0.5 is 0.688 dB (§2.2), so 4× cannot meet the ±0.2/−0.4 dBTP band by itself for signals with content near Nyquist; the EBU example filter is order 48 and the under-read table is what you quote when you choose the ratio.

### 6.3 The acceptance tolerance a correct implementation must hit

Primary source: **EBU Tech 3341** Table 1 (minimum-requirements test signals), quoted in §2.4 and §6.2(c) above. The tolerances are:

- **Loudness:** `M`, `S`, `I` = expected `±0.1 LUFS` (relative: `±0.1 LU`). Every loudness test case in the table (1–14) uses **±0.1 LUFS/LU**.
- **True peak:** `+0.2 / −0.4 dBTP` on tests 15–23 (i.e. a compliant meter may read up to 0.2 dB high, and must not read more than 0.4 dB low).
- **Loudness Range:** EBU Tech 3342 Table 1 uses **±1 LU** on its test signals (e.g. "LRA = 10 ±1 LU", "LRA = 15 ±1 LU").

So the acceptance gate for a BS.1770 implementation is **±0.1 LU** against the reference on the analytically-known and gated cases, **±0.1 LUFS** on the calibration signals, and **+0.2/−0.4 dBTP** on the true-peak cases. For a real (non-synthetic) program the same document's QC tolerance from EBU R 128 applies: **±0.2 LU** "in order to take account of measurement errors".

Also from Tech 3341 §2.9, the one-line calibration check to put in CI:

> "For a basic calibration and alignment check of signal level, a 1 kHz stereo sine-wave (signal applied in phase to both channels simultaneously), with its peak level at −18 dBFS, is recommended. **The meter should read −18.0 LUFS.**"

(And its warning: *"A frequency of 1 kHz is used, but as this frequency lies on a filter slope within the algorithm, the calibration is more critical than necessary…"* — so use 997 Hz / the exact coefficient set for the tight test and 1 kHz only for the sanity check.)

**Recommended proving harness for this repo (silent, no audio device), honouring `AGENTS.md` "Audio Safety":** a Node harness that stubs `AudioWorkletProcessor`/`registerProcessor`/`sampleRate`, feeds synthetic `Float32Array` blocks, and compares the resulting integrated loudness to (i) the analytic values in §1.8 and (ii) the `ffmpeg ebur128` values in §6.2(c)/(e). Acceptance: `|Δ| ≤ 0.1 LU` on the tests above.

## Appendix — the implementation in `audio/normalizer-worklet.js`, verified against the file

Evidence: `audio/normalizer-worklet.js`. **Cite style:** every reference below names the identifier, constant, or enclosing function the claim is about rather than a position in the file, and deliberately so — the file is edited concurrently, so line numbers rot and symbol names do not, and this appendix therefore never needs renumbering. (The file's own header comment claims a human-comfort loudness chain: gated ITU-R BS.1770-4 / EBU R128 measurement plus Film Standard levelling toward a fixed −20 LUFS program target; every point of that claim was checked against the code and against the standard, and it holds.) Earlier revisions of this appendix described a pre-rewrite exponential-window scheme and then a gated-only (−18 LUFS, slider-shifts-target) stage; neither scheme is in the file.

### What the file does, with symbol cites

1. **K-weighting: one 4th-order section = the two published stages convolved.** `initKCoeffs()` takes the libebur128 prototypes verbatim — shelf `f0 = 1681.974450955533`, `G = 3.999843853973347`, `Q = 0.7071752369554196`, `Vb = Vh^0.4996667741545416`, `K = Math.tan(Math.PI * f0 / sr)`; RLB high-pass `f0 = 38.13547087602444`, `Q = 0.5003270373238773` — then forms the returned `b0..b4` / `a1..a4` by exactly libebur128's products: its `b1: pb0 * -2 + pb1` ↔ `b[1] = pb[0]*rb[1] + pb[1]*rb[0]` with `rb = {1,-2,1}`, and its `a1: ra1 + pa1` ↔ `a[1] = pa[0]*ra[1] + pa[1]*ra[0]` with `pa[0] = ra[0] = 1`. In `process()` the per-sample recursion and the state shift taken *after* `y` reproduce the order in the `EBUR128_FILTER` macro (v0 from the old v1..v4; y from the new v0 and the old v1..v4; then shift). State lives in `this.filtV`, a `Float64Array(5)` per channel.
2. **Blocks: 400 ms, 100 ms hop, rectangular — no exponential smoothing.** `this.samples100 = Math.floor((sr + 5) / 10)` = 100 ms; `this.blockSize = this.samples100 * 4` = 400 ms; `this.shortWin = this.samples100 * 30` = 3 s (all set in `constructor()`). One ring, `this.pRing`, carries the running sums `this.sumBlock` (400 ms) and `this.sumShort` (3 s). In `process()` a block is retained when `this.hopCounter` reaches `this.samples100` and only once `this.pCount >= this.blockSize` — first block at 400 ms, then every 100 ms, 75 % overlap. This is §1.3 exactly.
3. **Channel weights and LFE.** `channelWeight(index, total)`: 1.0 for L/R/C, 1.41 for Ls/Rs, 0 for index 3 in a ≥6-channel layout; `process()` skips a zero-weight channel outright, so the LFE leaves both the filter and the power sum, matching BS.1770-4 Table 3. All channels still reach the output unchanged except for gain — correct, since the standard excludes the LFE from *measurement*, not from the signal.
4. **Gating chain.** `ABS_GATE_ENERGY = Math.pow(10, (ABS_GATE_LUFS + 0.691) / 10)` is libebur128's `histogram_energy_boundaries[0]`; `process()` never stores a block below it, which is exactly the standard's "gating blocks below the absolute threshold are not used in the relative gating calculation". `recomputeIntegrated()` means the retained (absolutely-gated) block energies, multiplies by `REL_GATE_FACTOR = Math.pow(10, -10 / 10)` — the `-0.691` cancels in that step, so this is Γr = (abs-gated loudness) − 10 LU — then averages the blocks at or above it and converts through `energyToLoudness()`, i.e. `10*log10(E) + LOUDNESS_OFFSET` with `LOUDNESS_OFFSET = -0.691`: BS.1770-4 Eq. (7).
5. **Slow gain is driven only by the LEVELLED gated integrated value.** In `process()` the desired gain is `targetLufs - integratedLufsLev` (fixed program target −20 LUFS — a judgment inside the published −20.0 to −16.0 LUFS window, corroborated within 1 dB by EBU R 128 s4's own cinematic remedy landing program at −21 LUFS), clamped so the TOTAL program gain (levelling + normalization) stays inside `MAX_BOOST_DB` / `MAX_CUT_DB` (+12/−20 dB) or `BLAST_GUARD_MAX_BOOST_DB` / `BLAST_GUARD_MAX_CUT_DB` (+6/−24 dB); it stays at unity until `this.totalFrames` reaches `WARM_SECONDS` *and* the levelled gated set is non-empty; the slew is asymmetric and in the log domain, `UP_TC_SECONDS` (3.0 s) rising and `DOWN_TC_SECONDS` / `BLAST_GUARD_DOWN_TC_SECONDS` (0.6 s / 0.35 s) falling. `set-gain-db` never moves the target: it arms `trimTargetDb`, an immediate output trim written into the delay line before the detector (ffmpeg loudnorm offset topology) with per-sample ramping, excluded from both measurements. `this.momentaryLufs` and `this.shortTermLufs` are telemetry only on the RAW program, and they are sliding *ungated* rectangular windows — which is the EBU Tech 3341 §2.2 definition of those two measures, correctly kept out of the integrated path.
6. **True peak and limiter.** `buildInterpPhases()` follows `interp_create` in structure (4x polyphase windowed-sinc, round-robin phases, `|c| <= 1e-6` skipped, phase `f = j % factor` with index `Math.floor(j / factor)`) with a longer sharper window: `taps = 97`, `factor = 4`, `half = (taps - 1) / 2`, `c = Math.sin(m * PI / factor) / (m * PI / factor)` with `c = 1` for `|m| <= 1e-6`, Kaiser window (beta = 6.0) instead of libebur128's Hanning `0.5 * (1 - Math.cos(2 * PI * j / (taps - 1)))`. `this.interpDelay = 25` is `(taps + factor - 1) / factor = (97 + 4 - 1) / 4` (a buffer size, not a latency; libebur128's 49-tap equivalent is 13). `interpPeak()` mirrors `interp_process`: it writes `this.interpZ[ch][this.interpZi] = x`, accumulates `pos = this.interpZi - indices[t]` wrapped by `+= this.interpDelay`, and `process()` advances `this.interpZi` once per frame. The raw sample is also entered as a candidate, which can only raise the detector and is safe (sample peak ≤ true peak). The ceiling is `CEILING_DB = -1` (`BLAST_GUARD_CEILING_DB = -2`) applied with a `TP_DETECTOR_MARGIN_DB` margin — the value is set in the worklet and is under active tuning, so this appendix deliberately names the symbol rather than pinning a number — i.e. `effCeiling = ceiling * dbToGain(-TP_DETECTOR_MARGIN_DB)`; the lookahead is `LOOKAHEAD_SECONDS` via `this.delayFrames`, and `process()` ends with a sample hard-clip to the ceiling.
7. **Real-time and interface invariants hold.** Every buffer is allocated in `constructor()`; `process()` contains no `new`, no array growth and no string building, and reuses a single `this.meterMsg` object — consistent with the Web Audio Spec's "arrays will be reused between calls so that no memory allocation is done" (§5.1). `Number.isFinite` guards cover the input sample, `v0`, `y`, `newP`, `framePeak`, the output sample and the AGC state. `resetMeter()` clears both meters, blocks, warm and program gain while keeping settings (including the trim). `registerProcessor('loudness-normalizer', …)` is preserved, the inbound handler is `this.port.onmessage`, and the message set is the original three plus `set-target-lufs`, `set-mode`, `reset-meter`; telemetry and meter messages additionally carry `userTrimDb`. `set-mode` is retained for compatibility and clears only the measurement — the levelling runs in both modes (one comfort chain).

### Independent check against BS.1770-4 Table 1 / Table 2

The file stores **one** 4th-order section, so it cannot be compared to the tables term by term (the tables give two biquads). The correct comparison is against the **product** of the two published biquads. Rebuilding those biquads from the §1.2 equations — which reproduce Table 1 and Table 2 to 15 significant digits at 48 kHz — and convolving them gives, at 48 kHz:

```
cascade b = 1.535124859586970 -5.761945908580321  8.116910049252581 -5.088481811112080 1.198392810852850
cascade a = 1.000000000000000 -3.680706748016390  5.087045247971131 -3.131546351446731 0.725208888477870
```

The worklet's `initKCoeffs(48000)` returns those numbers **bit-identically**: `max |worklet − cascade| = 0.000e+00` (and the same at 44.1 kHz). Equivalently, the worklet's section factors into a stage-1 biquad equal to Table 1 and a stage-2 biquad equal to Table 2 to every printed digit, and its own `b/a` give a K-weighting gain of **+0.691014 dB at 997 Hz** — the quantity BS.1770 Note 1 says the `-0.691` offset cancels.

**Verdict: the derivation is consistent with Table 1 and Table 2 — it matches this reference's independent derivation exactly, with no divergence.** The one rate-related difference is precise: because the prototype constants are rate-independent (as BS.1770 directs for non-48 kHz rates), the `-0.691` cancellation is exact at 48 kHz (+0.691014 dB) and off by **0.0028 dB at 44.1 kHz** (+0.693776 dB), so a 997 Hz mono reference reads 0.0028 dB high there. That is ~35× inside the ±0.1 LU acceptance band of §6.3, and it is the only numerical difference the derivation shows.

### Deviations and limits found (the check, not the summary)

- **Gate comparisons use `>=`** on energy (`e >= relThresh` in `recomputeIntegrated()`, `blockEnergy >= ABS_GATE_ENERGY` in `process()`) where the standard writes `lj > Γ`. A measure-zero difference; recorded so that no byte-identical claim against libebur128 is made.
- **`MAX_BLOCKS = 50000`** with the write-pointer wrap in `process()` makes the integrated value a sliding ~83-minute window (50 000 × 100 ms) past that point, not "over the duration of a programme" for multi-hour material. `recomputeIntegrated()` is O(blockCount) and is called from `process()` on every new block, i.e. quadratic over a long session — cheap in absolute terms, but the one place "integrated" is approximate.
- **Loudness Range is not implemented** (no Tech 3342 §1.6 output). True peak is reported as telemetry (`this.telemetry.truePeakDb`, the decaying hold on the delayed post-limiter output) AND drives the limiter as a control input: the undelayed detector reading (`framePeak` from `interpPeak()`) schedules the lookahead limiter gain. §1.6 and §2 remain reference material, not implemented features.
- The levelling stage (always on, one comfort chain in both modes) is a dead-band AGC on the RAW input (mechanism: ffmpeg loudnorm `INNER_FRAME` — inside ±`AGC_BAND_DB` (2.5 LU, OUR LRA-5.0 target for the EBU R 128 s4 LDR ≤ 5 LU outcome) no adaptation at all; outside, the spread is compressed back to the band edge), driven feedforward per sample from raw-input 3 s short-term vs raw-input gated integrated loudness, boost-capped at +`AGC_BOOST_CAP_DB` (6 dB, Dolby Film max boost) and TOTAL-clamped with the slow gain, with a relative-gate silence hold. It replaced the earlier Dolby Film Standard static curve (`FILM_*` thresholds + peak envelope): the absolute thresholds could not be re-anchored without a dialogue measure, while the dead-band adapts around the measured programme. The slow loop absorbs the difference by measuring the levelled signal. The `DynamicsCompressorNode` caveats of §5.4 still apply where a host prefers the built-in. LIVE COMPROMISE (EBU Tech 3343 §9.4.2 prefers offline/iterative adaptation; a browser tab cannot pre-pass): this is the live approximation, not offline-grade.
